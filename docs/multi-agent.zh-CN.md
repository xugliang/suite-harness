# 可选受控多 Agent 接入指南

Multi-Agent（多智能体）在 SuiteHarness 中是**可选的同产品任务委派**，不是 AB/ABC 产品组合的同义词。一个产品的主 Agent 可把一个有边界的任务交给预先配置的子 Agent 角色，子任务结果通过普通工具消息回到主 Agent；主 Agent 仍负责组织最终回答。没有启用的产品继续使用原来的单 Agent 工作流，产品 A/B 不需要因为框架增加委派能力而实现新接口。

这里的 `agent.delegate`（智能体委派）是框架受保护的只读工具，不是任意启动进程或让模型自由创建团队。第一版只允许**同一产品、最多两个子任务、深度一层**：子 Agent 不能再次委派，也不能转到另一个已购产品。子任务复用当前产品服务和统一执行器，不会为每个 Agent 新建容器。

## 两道开关

默认 `multi_agent.products` 为空，框架不会给任何产品开放委派。要启用，需要同时完成两项：

1. 在公司配置中为已购产品声明 `enabled: true` 与至少一个子角色。角色写明用途、子提示词、允许的工具别名和已经配置过的模型路由。
2. 在对应渠道 × 产品的 `ToolAccessTemplate`（工具访问模板）中，显式把框架工具 `agent.delegate` 加到 `read_aliases`（只读工具别名）。只配置角色而不授权工具，模型看不到也无法调用；只授权工具而未启用角色，委派被拒绝。

模型看到的工具参数只有 `role_id`（预设角色标识）和 `task`（最长 4096 字节的任务描述）。模型不能通过参数选择模型供应商、公司、产品、销售身份、命令、工作目录或授权令牌。**目前启用委派的产品需要在主提示词中简短列出已配置的角色 ID 与职责**，否则模型仅看到字符串参数，不一定知道应选择哪个角色；不要把客户秘密或授权数据写进角色说明。角色说明的自动发现仍待底座统一提供。

## 配置示例

以下片段放在公司配置文件的顶层；假设 `customer_bundle.products` 已选择 `product-b`，而 `models.routes` 已定义 `default`。工具别名必须是实际注册的工具名称。

```yaml
multi_agent:
  products:
    product-b:
      enabled: true
      max_children: 2
      max_depth: 1
      max_parallel: 2
      roles:
        - role_id: product_research
          instruction: "只完成交给你的产品资料检索任务，说明来源；不要猜测客户事实。"
          allowed_tools: [suiteharness.web.search]
          model_route: default
        - role_id: followup_draft
          instruction: "只起草沟通建议，不修改客户资料；需要客户事实时说明已获授权的依据。"
          allowed_tools: []
          model_route: default
```

部署模块再为允许委派的渠道和产品配置精确工具授权。例如仅让产品 B 的 Web 主 Agent 能委派：

```python
ToolAccessTemplate(
    channel_id="web",
    product_id="product-b",
    read_aliases=(
        "suiteharness.web.search",
        "agent.delegate",
    ),
    write_aliases=(),
    destructive_aliases=(),
)
```

若该产品也经飞书使用，需要单独决定是否给飞书 × 产品 B 的模板加 `agent.delegate`；Web 的授权不会自动复制到飞书。在上面这个只读模板示例中，子 Agent 无法获得写入、删除或 Bash 权限。若飞书模板另行允许特定目录的文件写入，子任务仍受同一父授权、路径白名单和执行策略约束，不会因委派自动扩大写权限。角色 `allowed_tools` 只是**上限**，子工具还必须位于父任务当前有效授权中；例如上例搜索工具没有进入父授权时，检索角色不会获得搜索权限。

`model_route`（模型路由）必须是 `models.routes` 中已有的路由，不能由模型临时改写。底座默认的产品路由 ReAct 工作流会按子角色选择该路由。若产品使用自定义 `Workflow`（工作流基类），须继承 `suiteharness.multiagent.service.RoleRoutedWorkflow`（支持角色路由的工作流抽象基类），实现 `with_role_route(role_id, model_route) -> Workflow`：根据角色 ID 和已验证路由返回用于该子任务的工作流。不满足此契约或返回的不是工作流时，框架拒绝委派，不会悄悄忽略角色路由。部署方仍需做该自定义实现的模型/工具契约测试。

## 实际执行边界

假设销售在产品 B 里问“给这位客户挑选礼物并拟一句跟进话术”。主 Agent 可把商品检索交给 `product_research`、话术草拟交给 `followup_draft`，再结合两个工具结果回答。子任务沿用真实发起人的公司、产品、渠道、销售主体和只读状态；产品 B 原有“销售只能查看自己客户”的业务校验仍要先于任何客户资料交给子 Agent。委派不是跨销售或跨产品共享画像的捷径。

框架为子任务签发短时、工具身份精确且不宽于父授权的新权限，统一执行器照常核对工具效果、审批、工作区、沙箱和网络出口。主任务与子任务共享迭代次数、工具调用次数和截止时间预算；并发受 `max_parallel` 限制。子任务完成、失败、取消或超时都有独立任务状态和父/子运行关联记录，不会把内部子会话直接显示成用户聊天记录。子结果作为标准 `tool message`（工具返回消息）交回模型，最终是否采纳由主 Agent 决定。

同一父运行中的同一工具调用若被重放，底座只在原授权仍有效、角色和任务内容未变，且授权令牌、可用子工具、销售/会话归属、渠道及只读状态均相同的情况下，复用持久化终态结果；不会再次启动子 Agent。换成更窄的新授权或另一个会话归属，即使销售账号和任务文本相同，也不会返回旧子任务的内容。服务崩溃时未确定完成的子任务被标记失败，不自动再次执行可能已有副作用的工具。

开启前至少验证：禁用产品不出现委派工具；未授权角色/工具被拒绝；飞书只读不能产生写操作；产品 B 的不同销售和不同客户无法借子任务访问彼此数据；父任务超时、取消和服务重启后没有重复执行或遗留运行。任务状态存于宿主的运行数据库而非用户会话数据库；SQLite 适合单服务器参考部署，多实例生产环境仍需协调与存储方案。
