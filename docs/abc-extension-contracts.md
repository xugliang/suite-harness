# ABC 扩展接口

SuiteHarness 的自有扩展接口使用 ABC（Abstract Base Class，抽象基类）。产品 A/B 和框架内置实现显式继承对应基类。现有接口的导入路径尽量保持不变，包括名称仍含 `Protocol` 的历史兼容入口；判断实际机制要看类定义，而不是文件名。

## 产品如何实现

必须实现的核心行为标记为 `@abstractmethod`。缺少实现时，Python 会在实例化时抛出 `TypeError`，而不是等收到用户请求后才发现方法不存在。

已有默认行为直接继承，例如反思策略默认原样返回决策，不持有外部资源的记忆提供者默认无需关闭资源。产品只覆盖确实不同的部分。数据库连接、线程等有资源的实现仍应覆盖关闭方法。

```python
from suiteharness.execution.protocols import ReflectionStrategy

class ProductReflection(ReflectionStrategy):
    pass  # 使用框架默认的“不额外反思”行为
```

## 后续如何给框架增加方法

如果新方法不是所有产品必备，不要加 `@abstractmethod`。提供合理的默认实现，老产品会自动继承，不需要修改。例如给已有抽象基类增加默认的诊断信息方法：

```python
def diagnostics(self) -> dict:
    return {}
```

如果功能不能提供有效默认行为，可放到单独的可选能力基类，调用方明确检查是否支持；或提供会抛出明确“不支持”异常的默认方法，并在调用边界处理。不能返回假成功。权限校验、隔离、撤销等安全操作不能默认放行。

若将所有产品都必须完成的新职责加入抽象方法集合，那仍是一次不兼容变更，需要适配产品。ABC 并不自动消除不兼容变更；兼容性来自“稳定必要接口 + 有默认实现的可选扩展”。

## 为什么仍可能看到 Protocol

少量 Protocol（结构化类型协议）只描述第三方 SDK、函数回调或内部消费方的最小视图，不是要求产品实现的正式扩展基类。例如工具处理函数可以直接是异步函数，第三方 Bedrock/Lark SDK 也不必继承框架基类。内部窄视图避免底层模块反向依赖服务器模块形成循环导入。

不要用 `ABC.register()` 或自定义 `__subclasshook__` 假装继承；它们不会让产品获得基类默认方法。

## 本次迁移不改变的行为

账号及客户隔离、长短期记忆配置、模型实时流式输出、工具权限检查、A 的知识查询及推送、B 的画像和问答流程保持原有业务逻辑。配置文件、数据库结构和业务数据不需要迁移。
